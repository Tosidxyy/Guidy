# P3 设计：跨计划时间冲突提示与合并

日期：2026-11-18
状态：已实施
范围：共享日历里，不同计划的块在同一时段重叠时提示用户；用户确认可以同时进行后，把两块合成为同时间、标题追加的块。

## 1. 背景

P1/P2 已让日历叠加所有计划：活动计划不透明，其他计划半透明且可直接拖动。P2c 之后，所有块的编辑都写服务端。

但两个计划各自独立求解，完全可能出现「考研计划的数学真题 07:00–08:00」与「健身计划的核心训练 07:30–08:30」落在同一时段。现在界面只是把它们并排画出来，没有任何提示；用户要么自己发现，要么在同一时间被塞了两件事。

用户提出的目标：**AI 要告知重叠；用户确认可以同时进行后，自动合成一个任务块，任务名字追加。**

## 2. 目标与非目标

### 目标

- 检测活动计划与其他计划之间的时间重叠，在日历上直接提示。
- 用户确认后一键合并：两块对齐到同一时间窗，标题变成「A + B」，两边都写服务端、可撤销。
- 已合并的两块在日历上只画一张卡，不再反复提示。
- AI 在对话里能感知这些重叠，并在相关时提一句。

### 非目标

- AI 直接修改其他计划（P4）。
- 跨计划原子事务：每个计划有自己的 version，合并是两次 patch，第二次失败会明确报告已合并了一半。
- 自动合并（不询问）：用户必须确认。
- 把两条任务定义合回一条：合并只处理块的时间与标题，任务定义不动。

## 3. 方案选择

| 方案 | 结论 |
| --- | --- |
| A. 块级对齐 + 标题追加，判据「同时间同标题即已合并」 | **采用**。复用 `update_block`（title/start_utc/end_utc 同一 op），不新增表、不改版本模型；每侧独立可撤销。 |
| B. 新建「组合块」实体跨计划引用两边 | 不采用。要引入跨计划引用与级联删除，和 per-plan version 冲突，收益只有省一次写。 |
| C. 只在 AI 对话里提醒，由 AI 合并 | 不采用。AI 无法原子保证；且用户要的是「日历上确认」。AI 负责说，界面负责做。 |

## 4. 冲突判定

`shared/engine/conflicts.ts`：

```ts
interface ConflictPlan { id: string; title: string; blocks: Block[] }
interface PlanConflict {
  key: string;                 // 稳定排序后的 "planId|blockId" 组合
  a: { planId; planTitle; block };
  b: { planId; planTitle; block };
  overlap_min: number;
  start_utc: string;           // 两块并集窗口
  end_utc: string;
  merged_title: string;        // "A + B"（标题相同则保持一个）
}
findConflicts(plans, opts?: { onlyPlanId?: string }): PlanConflict[]
```

规则：

- 只比较**不同计划**之间的块。
- 重叠分钟数 > 0 才算冲突；首尾相接（08:00 结束 / 08:00 开始）不算。
- **已合并判据**：起止完全一致且标题相同 → 视为同一条合并块，不再提示。判据不新增字段，客户端画布与服务端提示共用。
- 输出按开始时间排序，`key` 由两侧 `planId|blockId` 排序后拼接，保证稳定。

## 5. 合并

```ts
mergeConflictOps(c): { planId: string; ops: ApplyOp[] }[]
```

每侧一个 `update_block`：`{ title: merged_title, start_utc: c.start_utc, end_utc: c.end_utc }`。

- 先写**非活动计划**，再写活动计划：非活动侧失败时，用户当前看到的计划还没被改。
- 每侧沿用 P2b/P2c 的 `planController.apply`（乐观更新 → 服务端校验 → 历史记录）。
- 合并后 toast 的「撤销」依次撤销两侧的该条历史（两个计划各一条）。
- 合并窗口取**并集**：07:00–08:00 与 07:30–08:30 合并为 07:00–08:30，两边的实际时间都不丢。

## 6. 界面

日历顶部新增冲突条（不遮挡网格）：

```
⚠ 与「健身计划」有 1 处时间重叠      查看 / 全部合并
```

展开后每条：

```
11/19 07:00–08:00  数学真题 + 核心训练（健身计划）   合并  忽略
```

- 「忽略」只在本次会话内记在组件状态，刷新后重新提示。
- 合并后两块同时间同标题，画布只画活动计划那张卡；其他计划层里同款块不再重复绘制。
- footer 的「含其他计划 N」按可见的外计划块计数。

## 7. AI 感知

`buildUserMessage` 增加可选 `conflicts` 参数，命中时追加：

```
【共享日历：跨计划时间重叠】
- 11/19 07:00–08:00：当前「数学真题」×「核心训练」（健身计划）
若与用户当前请求相关，用一句话提醒；不要自行修改其他计划，合并由用户在日历上确认。
```

服务端只取与活动计划 horizon 相交的其他计划（通常 1–3 个）来计算，避免每次对话扫全库。

## 8. 测试与验收

### 单元

- 跨计划重叠检测、首尾相接不算、同计划不算、`onlyPlanId` 过滤、排序稳定。
- 已合并（同时间同标题）不再计为冲突；标题相同不重复追加。
- 合并 op：两侧各一条 `update_block`，携带并集窗口与追加标题。
- `collectForeignBlocks` 隐藏与活动块同时间同标题的外计划块。
- `buildUserMessage` 有冲突时包含冲突段，无冲突时不出现。

### 浏览器

1. 两个计划各有一块落在同一时段 → 冲突条出现，文案含另一计划名。
2. 点「合并」→ 两块时间对齐、标题为「A + B」，刷新后保持。
3. 冲突条消失，日历上只看到一张卡。
4. 撤销 → 两侧都回到合并前。
5. 在一个计划的对话里发消息，AI 能提到该重叠（依赖模型，只做人工观察）。

### 验收标准

- 重叠必被提示，不重叠不提示；
- 合并写服务端且两侧可撤销；
- 已合并不重复提示；
- 既有 344 测试保持全绿。

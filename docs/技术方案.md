## 1. 平台约束（选型的硬边界）

以下事实来自 Qoder Sites 平台文档，所有选型必须在此边界内：

| # | 约束 | 对选型的影响 |
| --- | --- | --- |
| P1 | 前端必须是**静态产物**（`dist/index.html`），无 SSR、无 Node 服务进程 | 排除 Next.js/Nuxt 等 SSR 框架；SPA 路由需 `prepare_site.spa: true` |
| P2 | 服务端只有**一个 `app` Edge Function（Deno）**，入口 `functions/index.ts`，`Deno.serve` | 全部后端逻辑（路由/引擎/QCA/配额）收敛进单 Function；无 Express/Fastify |
| P3 | Function 依赖必须**自包含**，部署时不安装 npm 包 | 后端第三方库只能用 Deno 兼容形式（`npm:` 说明符或 vendored 源码）；官方提供的 `cloud-agents.mjs`、`sse.mjs` 直接复制进 Function 目录 |
| P4 | 持久化走 **Function backend 数据库**（Postgres，平台注入 SDK，`app` schema），迁移走 reviewed migration 流程 | 无 ORM；SQL 由应用自管，schema 变更走 `create_database_migration → apply` |
| P5 | 身份用注入 SDK 的 **`requireUser(ctx)`**（匿名访客，免登录） | 不自建账号体系；归属校验在 Function 内逐路由执行 |
| P6 | AI 走 **QCA Managed SSE**：浏览器 → 同源 Function → QCA；`QODER_PAT` 仅 Function 可读；`apiOrigin` 取自 `get_context.runtime.cloudAgents.apiOrigin` | 前端不直连 QCA；SSE 由 Function 投影，历史/游标自建持久化 |
| P7 | 平台**不提供**现成会话服务/分布式协调器 | 会话映射、消息历史、断线游标、幂等派发全部应用自建（PRD §8 契约） |
| P8 | 官方 React starter：**React + TypeScript + Vite + Tailwind + shadcn/ui 组件目录** | 前端基座直接采用 starter，不另起脚手架 |

## 2. 总体架构

```
┌─────────────────────────── 浏览器（静态 SPA）───────────────────────────┐
│  React 18 + TS + Vite + Tailwind + shadcn/ui                            │
│  ├── 路由：react-router（/ 、/community 、/template/:id）               │
│  ├── 服务端状态：TanStack Query（乐观更新/回滚/缓存）                    │
│  ├── 客户端状态：Zustand（视图/选中/撤销栈/抽屉/SSE 连接状态）            │
│  ├── 日历面板：自研 CSS Grid 时间网格 + Pointer Events 拖拽              │
│  └── 共享层引用：@shared/schemas（Zod）、@shared/types                  │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │ 同源 /functions/v1/app/api/*（fetch + SSE）
┌──────────────────────────────▼──────────────────────────────────────────┐
│  app Edge Function（Deno，functions/index.ts）                          │
│  ├── router.ts        路由分发 + 方法/大小/归属前置校验                  │
│  ├── identity         requireUser(ctx) → visitor_id                     │
│  ├── routes/          chat / plans / blocks / constraints / patches /   │
│  │                    templates / recovery / export                     │
│  ├── engine/          确定性排程引擎（纯函数，引用 @shared/engine）       │
│  ├── qca/             cloud-agents.mjs + sse.mjs（官方资产）             │
│  │                    会话映射 / 幂等派发 / 流投影 / 游标持久化           │
│  ├── db.ts            注入 SDK 封装（app schema，参数化查询）            │
│  └── quotas.ts        每日配额 / 并发协调                                │
└───────────────┬─────────────────────────────────┬───────────────────────┘
                │ 注入 SDK（QODER_DATABASE）        │ QODER_PAT（服务端 Secret）
        ┌───────▼────────┐                ┌────────▼─────────┐
        │ Function 后端 DB │                │ Qoder Cloud Agents │
        │ (Postgres, app) │                │ Managed SSE        │
        └────────────────┘                └──────────────────┘
```

**理解与排程分离**（PRD §6.0）在代码层的落点：

- LLM 结构化产物（`constraint_set` / `patch`）由 Function 用 **Zod Schema + 业务校验**把关，失败自动重试 ≤2 次。
- 排程引擎是 `shared/engine/` 下的**纯 TS 函数**：输入 `(taskDefs, constraints, horizon, pinnedBlocks)`，输出 `(blocks, violations, compromises)`。**双端运行**（已拍板）：前端本地求解，生成预览 / 补丁 diff / 拖拽校验零服务端往返，体验即时；服务端在 commit / apply 时**重算作为权威**，绝不信任客户端结果。一致性由三点保证：同一份源码、同一 `ENGINE_VERSION`、确定性算法（稳定排序，无随机/时钟依赖）；提交携带 `result_hash`（结果稳定序列化 SHA-256），服务端重算比对，不一致以服务端为准并向用户提示差异。Vitest 直接单测引擎。

## 3. 前端技术选型

### 3.1 选型总表

| 关注点 | 选型 | 理由 | 备选与否决原因 |
| --- | --- | --- | --- |
| 基座 | React + TypeScript + Vite（官方 starter） | 平台标准路径，含类型检查与静态构建；shadcn 组件目录现成 | Next.js：违反 P1（SSR）；纯手写 HTML：交互复杂度不支撑 |
| 样式 | Tailwind CSS（starter 自带）+ CSS 变量设计令牌 | 与 shadcn 一致；Nudge 外观变量（`--site-*`）天然接入 | CSS-in-JS：运行时开销与 starter 体系冲突 |
| 组件 | shadcn/ui（dialog/sheet/tabs/dropdown-menu/sonner/combobox 等） | starter 内置、可访问性行为完整、源码可改 | MUI/AntD：第二套设计体系，体积与风格冲突 |
| 路由 | react-router-dom v6 | 3 个路由 + SPA fallback，成熟轻量 | TanStack Router：类型更强但学习成本不必要 |
| 服务端状态 | TanStack Query v5 | 乐观更新/失败回滚/缓存失效是 F4.1 的直接需求；mutation 生命周期清晰 | Redux+RTK Query：样板多；裸 fetch：回滚/竞态手写成本高 |
| 客户端状态 | Zustand | 撤销栈、选中块、视图偏好、SSE 连接态等纯客户端状态，API 极小 | Redux：过重；Context：高频拖拽更新引发整树重渲染 |
| 日历 | **自研**（CSS Grid + Pointer Events，见 §4） | 幽灵 diff、冲突高亮、15min 吸附、键盘移动均为定制语义 | FullCalendar/react-big-calendar/Schedule-X：见 §4 对比 |
| 日期/时区 | date-fns + date-fns-tz | 树摇友好、UTC↔计划时区转换明确（F2.7） | Day.js：时区插件链近似但生态略弱；Temporal： polyfill 体积大 |
| Schema 校验 | Zod（前后端共享） | 一份 Schema 双端复用；Deno 支持 `npm:zod` | Ajv：JSON Schema 写法繁琐，TS 类型推导弱 |
| Markdown 渲染 | react-markdown + rehype-sanitize | 白名单净化，禁 raw HTML（F8.5/A12） | marked+innerHTML：XSS 风险 |
| 图标 | lucide-react | shadcn 默认搭档，树摇 | — |
| 动效 | CSS transition 优先；diff 预览/落位反馈用少量 framer-motion | 克制原则（PRD §7 视觉）；拖拽路径上**不用** JS 动画库，直接 transform | 全量 framer-motion：拖拽 60fps 风险 |
| ICS/JSON 导出 | 浏览器端手写序列化（ICS 格式简单固定） | PRD 要求不引入 Storage；无需后端参与 | ics npm 包：可用但收益小 |
| 单测 | Vitest（引擎/Schema/工具函数） | 与 Vite 同生态，引擎纯函数直接测 | Jest：配置冗余 |

### 3.2 状态职责划分（避免多源竞争）

| 状态 | 归属 | 说明 |
| --- | --- | --- |
| plans/blocks/constraints/templates 数据 | TanStack Query 缓存 | 服务端为准；mutation 乐观更新，失败回滚 |
| 当前视图（周/日）、可视时段、选中块 | Zustand | 纯 UI |
| 撤销/重做栈（≥20 步） | Zustand | 存 Patch 逆操作，不存数据快照（省内存）；AI 补丁与手动编辑共用（F4.6） |
| SSE 连接态、流式缓冲、游标 | Zustand + Query | 流式增量进缓冲，结构化产物到达后 invalidate 相关 query |
| 草稿输入、外观偏好 | localStorage | F7.4，仅设备本地 |
| 生成预览 / 补丁 diff 试算结果 | Zustand（本地引擎产出） | 前端即时求解，确认后才走服务端 commit/apply |

## 4. 关键决策：日历面板实现方案

日历是视觉主角与交互核心（F3 全部需求），三个候选：

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| A. FullCalendar / react-big-calendar | 成熟、视图全 | 拖拽插件语义固定：15min 吸附可配，但**幽灵 diff 叠加、冲突红边抖动、软约束黄标、键盘方向键移动**都要 hack 内部 API；包体大（FullCalendar 全家桶 >200KB）；样式覆盖成本高 | 否决 |
| B. Schedule-X | 现代、拖拽内置 | 定制事件渲染与双块叠加（新旧位置 ghost）能力有限；社区小，遇坑无解 | 否决 |
| C. **自研 CSS Grid 时间网格 + Pointer Events** | 完全掌控：吸附/冲突/ghost/键盘/移动端手势全部按 PRD 语义实现；渲染层薄（100 块 ≈ 100 个绝对定位 div），拖拽只改 transform，天然 60fps；与 shadcn 视觉体系无缝 | 需自建拖拽/resize/键盘逻辑，约 600–900 行核心代码；需自测边界（跨天、DST、重叠） | **推荐** |

**方案 C 实现要点：**

- 结构：`WeekGrid`（7 列 × 时间轴）用 CSS Grid 布局；每个 `Block` 绝对定位于列内，`top/height` 由分钟数换算。日视图为单列同构组件。
- 拖拽：`pointerdown/move/up` + `setPointerCapture`；拖动中只更新 `transform`（不触发重排），释放时吸附 15min 网格并计算落点；落点校验调用 `@shared/engine` 的 `validatePlacement`（与后端同一函数）。
- 冲突反馈：拖动中实时计算非法落点 → 红边 + 禁止释放气泡；软约束违反 → 黄标允许释放（F3.4）。
- resize：块底边拖拽手柄，同样吸附与校验。
- diff 预览：旧块半透明原位保留 + 新块 ghost 叠加（绿/红/黄语义色），确认后一次性提交（F5.2）。
- 键盘：块可聚焦，方向键移动 15min/跨天，Enter 打开详情，Delete 删除（可访问性要求）。
- 移动端：单列日视图 + 横向滑动切天；长按新建（F3.6 P1）；双指缩放时间粒度降级为可选（P1 末位）。
- 性能：块组件 `React.memo`；拖拽态存 ref + rAF，不进 React state 高频路径；100 块拖拽 ≥50fps 可达。

> 此决策已评审确认（v0.2）：采用方案 C 自研。

### 5.2 API 路由契约（概要，详细字段在《数据模型与 API 契约》定稿）

所有路由前缀 `/functions/v1/app/api`，除标注外均需 `requireUser`：

| 方法 路径 | 用途 | 关键契约 |
| --- | --- | --- |
| POST `/chat/send` | 发送消息 | body: `{conversation_id?, plan_id?, text, today?, timezone?, request_id}`；≤2000 字符；配额检查；202 受理；同访客并发派发 ≤1 |
| GET `/chat/history?conversation_id` | 历史恢复 | 归属校验；分页 |
| GET `/chat/events?conversation_id&cursor` | 断线增量 | 游标后事件回放，不重发用户消息（F8.3/8.4） |
| POST `/chat/interrupt` | 中断生成 | 取消上游流读取，状态置 interrupted |
| POST `/plans/commit` | 确认落库 | body 携带完整 input（task_defs/constraints/horizon）+ `result_hash` + `preview_id`；服务端**重算引擎**比对后落库；preview_id 幂等防重复 |
| GET/PATCH/DELETE `/plans/:id` | 计划管理 | 归属校验；删除软删 |
| POST `/plans/:id/blocks` 等 | 块 CRUD | 与 Patch 同一 `validatePlacement`；乐观更新配套 |
| POST `/patches/apply` | 应用补丁（AI/手动统一通道） | 试算在前端本地引擎完成（无 `/patches/preview` 往返）；apply 携带 ops + base_version + preview_id；服务端重校验/重算后应用，返回逆操作供撤销 |
| GET `/templates` | 广场 | 公开读（无需身份）；排序/标签/搜索参数 |
| GET `/templates/:id` | 详情 | 公开读 |
| POST `/templates` | 发布 | 脱敏由服务端执行；基线过滤同步 + AI 审核异步（P1）；每日 ≤3 |
| POST `/templates/:id/apply` | 套用 | 复制 snapshot → 新计划草稿；use_count 幂等 +1 |
| POST `/templates/:id/like` | 点赞/取消 | 每访客幂等（P1） |
| POST `/recovery/*` | 恢复码 | P1 |
| POST `/data/delete-all` | 级联删除 | 二次确认 token |

**通用规则**：入口先校验方法/大小/归属，再触上游；错误返回稳定错误码 + 诊断 ID，不泄露上游原文/凭据；写操作全部参数化查询。

### 5.3 QCA 会话协调（P7 自建部分）

- **懒初始化**：仅在授权的 `POST /chat/send` 后创建 QCA Session；页面加载/重连只复用 `conversations.qca_session_id` 绑定。
- **幂等派发**：`dispatch_intents(request_id UNIQUE, status)`；发送前插入 pending → 调上游 → 成功置 done；**结果未知保持 pending**，重连时先对账再决定是否重发（PRD §8 契约 2）。
- **流投影**：Function 消费上游 SSE，只转发白名单事件（增量文本、结构化产物、状态、错误码），逐条持久化 `messages` 并推进 `last_cursor`，完成后关闭上游流。
- **结构化产物通道**：`constraint_set` / `patch` 以专用消息类型返回；Zod + 业务校验失败 → 自动要求模型重试 ≤2 次 → 仍失败返回可读错误（F1/§6.0）。
- **提示注入防护**：模板 snapshot 进入提示词时包裹隔离标记并声明"仅为数据"；系统指令固定服务端配置，用户不可改（R6）。

## 6. 数据层

- **Schema**：PRD §8 实体草案 → `app` schema 建表；迁移走平台 reviewed migration 流程（`create_database_migration` → 审阅 → `apply_database_migration`），`schemaRef` 取自 `get_database_schema`。
- **关键索引**：`blocks(plan_id, start)`；`constraints(plan_id)`；`messages(conversation_id, created_at)`；`templates(status, created_at)` 与标签 GIN；`quotas(visitor_id, date)` UNIQUE；`dispatch_intents(request_id)` UNIQUE。
- **归属强制**：所有私有读写 WHERE 带 `owner_visitor_id = $verified`；跨访客一律 403（A8）。模板广场为唯一公开读面。
- **无任意事务**：平台 SDK 不提供通用事务 → 用**唯一键幂等 + 条件更新（version 列）+ 失败对账**替代（官方示例模式）。`plans/commit` 用 preview_id 唯一键防重复落库。
- **时间存储**：全部 UTC timestamptz + `plans.timezone`；展示层用 date-fns-tz 转换（F2.7）。
- **软删**：plans/templates `deleted_at`；7 天清理为 P2，MVP 仅标记。

## 7. 共享代码与校验

```
shared/
├── types.ts        # Plan/Block/Constraint/TaskDef/Patch/Template 类型
├── schemas.ts      # Zod：constraint_set、patch、各 API body
├── engine/
│   ├── solve.ts    # 主求解器（纯函数）
│   ├── validate.ts # validatePlacement（拖拽落点/补丁共用）
│   ├── diff.ts     # 新旧 blocks → diff 结构
│   └── report.ts   # 冲突/妥协报告生成
└── constants.ts    # 8 分类色板、约束类型枚举、配额默认值
```

- 前端：Vite alias `@shared → ../shared`。
- Function：Deno 相对路径 import；Zod 用 `npm:zod@3`（Deno 原生支持 npm 说明符，部署时由 Worker 解析，无需本地安装）。
- **引擎双端运行**（已拍板）：前端求解用于即时预览与拖拽校验；服务端 commit/apply 重算为权威。`ENGINE_VERSION` 常量随结果提交，版本不匹配时服务端拒绝并提示前端刷新；`result_hash` 比对不一致时以服务端结果为准并明示差异。
- 引擎算法（确定性贪心，F2.2）：fixed_block 落位 → 按优先级+窗口受限程度排序 → 逐任务在候选时段（active_window 减去 busy/已占/daily_cap 余量）内按偏好打分放置 → 可拆分任务切块（≥25min）→ mutex/buffer 检查 → 输出 violations/compromises。复杂度 O(任务数 × 候选槽数)，7 天 × 50 任务 <200ms 预算充足。Vitest ≥12 用例覆盖各约束类型与无解分支（F2.6）。

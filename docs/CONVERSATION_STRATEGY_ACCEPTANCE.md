# 聊天制订与21天策略验收（2026-10-17）

依据用户本轮明确要求更新[PRD](PRD.md)、[架构](ARCHITECTURE.md)与[UI设计](UI_DESIGN.md)。此范围是聊天制订、策略确认与内置日历，不代表提醒/反馈完整V0.1或上架完成。旧卡片版本的iPhone通过反馈不充当新版真机证据。

## 交付映射

| 用户行为 | 实现与边界 |
| --- | --- |
| 与Agent自然聊天，三轮后制订 | GuidyCards左右对话与紧凑输入；服务端验证三次已答回合，第三次可随制订提交；未知/委托允许继续。首问题失败有明确恢复入口。 |
| 先浏览21天策略 | strict工具使用week1/week2/week3固定内容槽，程序编译3×7天和任务编号；每周一个练习单元，单元拆成1–3个具体行动。不是让用户填写slot。旧周期只读兼容。 |
| 继续讨论或接受 | 讨论是独立持久会话，可回答、提议修改或新增事件。确认修改进入既有版本化工作流；接受策略才写核心计划/日历。 |
| 日历日期下的时间卡片 | 复用激活版本投影与分钟分段；显示起止时间、标题和做法，历史完成/跳过保留。 |
| 手动添加 | 日期、半小时步长的开始/结束时间和名称；无需模型，确定性冲突与revision检查。 |
| 在原方案聊天中添加 | Agent输出明确日期、当地时刻与时区；程序转换UTC毫秒，校验真实日期/未来时段，用户确认后写入。日期不明先追问。 |

## Harness的程序边界

模型不获得核心写入能力。问答/讨论/研究/生成均有状态、本人归属、版本、持久预留、上下文限长与额度；同键回读不重发模型，未知结果不自动付费重试。讨论限个人20次/全局60次每日、每目标60条，独立于现有澄清/生成额度。

21天输出编译后必须通过来源/结构/分段检查与确定性容量预检；每次时长、每周频次和排除星期必须可排入建议窗口。预检使用空占用周期，只验证内部一致性；真实日历占用在候选和确认时再核对。手动/聊天新增事件的插入、回执、revision变更同一D1事务；错误/冲突不写半份日程。

迁移0020仅增加conversation_turns/calendar_event_receipts，已在本地和云端应用，没有删除已有计划或用户历史。云端Worker/Workflow版本：`6aceb9e2-c065-47b0-9f2c-f85050a8f270`。

## 自动检查与真实链路

- 后端最终全量126/126通过，覆盖迁移、归属、并发/幂等、预算、策略编译/容量、无效日期、明确确认、不可变版本与历史；typecheck/lint/format:check/build:cloud通过。
- 移动端30/30状态用例通过，最终typecheck/lint与iOS资源导出通过。导出不代表已生成签名包。
- 云端真实新目标经过三个DeepSeek问题、豆包检索、研究判断/严格策略生成，得到三个阶段、三个单元、12次可排安排、0未安排；完整第三题尾部“周三没空”进入冻结上下文，实际未排周三。确认前PlanVersion为0，明确接受后恢复正确。
- 同次真实讨论生成次日北京时间10:00–10:30散步提案，确认前无固定事件，确认后恰好一条，实际UTC毫秒与请求时间一致。该次6个模型调用（问题3、研究/生成2、讨论1），无真实邮件；不是本轮所有调查尝试的累计用量。
- Browser plugin not available，采用Playwright/Edge，393×852与320×480。测试传输桥将本地UI请求送往真实云API，仅测试进程持有隔离会话；没有更改部署CORS，不冒充原生Cookie/网络验证。测试身份以随机example.invalid邮箱创建，结束按邮箱/ID精确清理。

初次联测发现多单元依赖导致16项排不下，随后容量预检拒绝另一份不合理输出；进一步改为程序拥有固定周结构，而非只加提示词。另一次首问题AI_INVALID_RESPONSE暴露启动失败恢复入口缺失，已补明确恢复。最终真实链路末尾测试脚本选择了下个月日期却未先翻月，截图又碰到状态刷新，因此该脚本整体不记为通过；已验证到的模型、策略和日程写入事实与后续零模型界面验证分开记录。

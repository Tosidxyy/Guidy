## 1. 产品概述

### 1.1 一句话定位

Guidy 是一个**免登录**的 Web 应用：用户用自然语言说出自己的目标和生活节奏，AI 智能体自动提取时间与互斥等约束，结合领域知识生成个性化计划，并落在一个可拖拽编辑的日历面板上；计划可手动编辑、可继续用对话微调，满意后可一键发布到社区成为他人可复用的模板。

### 1.2 背景与问题

市面上的计划 / 自律类产品普遍存在三个断层：

1. **输入断层**：要求用户手动逐项填表，或直接套用他人模板，无法表达"我周三晚上要接孩子""考研冲刺期每天最多学 6 小时"这类真实生活约束。
2. **排程断层**：模板是静态的，不会根据用户的时间窗口、任务互斥、精力上限自动重排，冲突全靠用户自己发现。
3. **沉淀断层**：个人摸索出的好计划难以结构化地分享，社区里流通的多是截图和 PDF，无法"拿来即用再个性化"。

### 1.3 差异化主张

- **对话即输入**：说人话，不填表。AI 负责理解，确定性排程引擎负责落位，二者分工（见 §6.1）。
- **约束是一等公民**：时间窗口、互斥、每日上限、缓冲、偏好时段等被显式建模、可视化、可编辑，而不是藏在提示词里。
- **计划是活的**：日历上拖拽即改，对 AI 说"把跑步挪到早上"即改，改动先预览后生效。
- **模板是活的**：社区模板不是截图，而是"约束 + 任务结构"的可执行快照，套用后按新用户自己的约束重新排程。
- **零门槛**：无注册、无登录，打开即用；匿名身份 + 恢复码保障数据可找回。

### 1.4 产品原则

| 原则 | 含义 |
| --- | --- |
| LLM 负责理解，引擎负责排程 | 大模型只做需求理解、约束提取、编辑意图转译；所有时间落位由确定性引擎计算，杜绝"幻觉时间"与约束违规 |
| 先预览，后生效 | AI 生成的计划与 AI 编辑补丁，都必须以可视化 diff 呈现，用户确认后才写入日历 |
| 免登录 ≠ 无归属 | 每个匿名访客有服务端可验证的身份，私有数据严格按归属隔离 |
| 冲突显式化 | 无解的约束不静默丢弃，明确告知用户"哪条约束放不下、为什么、建议怎么改" |
| 分享先脱敏 | 发布模板前自动剥离个人化信息（具体日期、私密备注），只保留结构与相对时间 |

## 2. 目标用户与核心场景

### 2.1 目标用户

| 用户群 | 典型诉求 |
| --- | --- |
| 备考学生（考研 / 考证 / 语言考试） | 长周期复习计划，科目互斥、每日学习上限、模考日固定 |
| 职场自我提升者 | 工作之外的健身 / 阅读 / 副业计划，通勤与加班时间不确定 |
| 生活管理者 | 育儿、家务、就医、宠物照料等碎片化事务的周计划 |
| 模板消费者 | 不想从零描述，直接套用高分模板再按自己情况微调 |

### 2.2 核心场景（Golden Path）

> 小林备考 12 月的研究生考试。她打开 Guidy，不注册，直接输入："我 12 月 20 日考研，每天最多学 6 小时，周三晚上和周六下午要兼职，数学和英语不要安排在同一天连续学，早上背单词效率最高。"
>
> Guidy 流式回复并追问关键缺口（当前水平、每日可用时段），随后给出一张**约束确认卡**：考试倒计时、每日 6h 上限、两个固定忙碌窗口、数学/英语互斥、早晨偏好时段。小林确认后，右侧周日历上自动落位了未来一周的复习块，冲突为零。
>
> 她把周四的"政治"拖到周五上午，又对 AI 说"这周加两次 40 分钟跑步"，AI 给出改动预览，她点确认。满意后她点击"发布为模板"，系统脱敏生成《在职考研 6h/日冲刺周计划》，进入社区。
>
> 另一位访客在社区套用该模板，输入自己的忙碌窗口，引擎按他的约束重新排程——同一结构，不同的计划。

### 2.3 次要场景

- 回访用户打开站点，自动恢复上次的计划与对话历史。
- 用户换设备 / 清浏览器数据后，凭恢复码找回计划。
- 用户导出计划为 `.ics` 日历文件 / JSON 备份。
- 计划执行中临时有事，对 AI 说"今天加班到 9 点，重排今天剩下的安排"。

**平台能力边界（PRD 层面必须遵守）：**

- 持久化使用 Function 后端数据库（新项目不使用 legacy database 直连）；文件类需求（如导出）优先浏览器端生成，不默认引入 Storage。
- QCA 会话与访客的映射、消息历史、断线恢复游标必须由应用自建持久化协调（平台 SDK 不提供现成的会话服务）；同一访客并发发送需服务端协调，未知结果的派发保持 pending 直至对账。
- 开启 Qoder 后端会自动创建平台 PAT 并配置为服务端 Secret，**实施前需用户显式确认**（开发阶段任务，不在本文档展开）。
- 匿名身份的设备绑定特性意味着"清数据即失联"，必须提供恢复码机制（见 F7）。

## 4. 术语与核心概念

| 术语 | 定义 |
| --- | --- |
| 计划 Plan | 一次规划产物，含标题、时间范围（默认未来 7 天，可选 14 天；MVP 不含 30 天）、时区、任务块集合、约束集合 |
| 任务块 Block | 日历上的一个时间块：标题、分类、起止时间、优先级、固定/灵活标记、备注 |
| 约束 Constraint | 结构化规则（见 §6.2），来源为用户明示或 AI 提取（需确认），可单独增删改 |
| 排程 Scheduling | 确定性引擎将"待安排任务 + 约束"求解为日历落位的过程 |
| 对话 Conversation | 访客与 Guidy 智能体的一次多轮会话，绑定到某个计划（或创建计划前） |
| 编辑补丁 Patch | AI 编辑产出的结构化操作列表（增/删/改/移任务块、改约束），经校验与预览后应用 |
| 模板 Template | 脱敏后的计划结构快照（相对时间 + 约束 + 任务定义），可被他人套用并重新排程 |
| 恢复码 Recovery Code | 匿名访客的一次性展示凭证，用于跨设备/清数据后认领自己的数据 |

## 5. 信息架构与页面

站点为单页应用（SPA），公开访问，共 3 个路由 + 全局抽屉：

```
/                工作台（核心页面，默认落地）
├── 左栏：对话面板（流式消息、约束确认卡、计划生成预览、编辑 diff 预览）
├── 右栏：日历面板（周视图默认 / 日视图切换，任务块拖拽、冲突标记）
├── 顶栏：Guidy 标识、计划标题与时间范围、视图切换、社区入口、设置抽屉入口
└── 抽屉：约束清单编辑器、计划列表（多计划）、导出、恢复码、外观设置

/community       社区模板广场（卡片流、标签筛选、排序、搜索）
/template/:id    模板详情（结构预览日历、约束说明、套用按钮、使用数/点赞数）
```

**首屏即工作台**：不做营销落地页。首次访客看到已填充的示例计划（明确标注"示例"）+ 对话输入框与引导语（"说说你的目标和时间安排，我来帮你排"），一键清空示例开始自己的规划。

**响应式**：桌面双栏（对话 38% / 日历 62%）；移动端上下堆叠 + 底部 Tab 切换"对话 / 日历"，日历支持横向滑动与双指缩放时间粒度。

## 6. 功能需求

优先级定义：**P0 = MVP 必须（大赛演示依赖）；P1 = 完整体验应有；P2 = 加分项，时间允许再做。**

### 6.0 核心架构原则：理解与排程分离

```
用户自然语言
   │  QCA 智能体（SSE 流式）
   ▼
结构化产物：任务定义 + 约束 JSON（Schema 校验）
   │  确定性排程引擎（shared 纯函数，双端运行：前端即时预览，服务端权威重算）
   ▼
日历落位方案（含冲突/无解报告）
   │  前端 diff 预览 → 用户确认
   ▼
写入计划（乐观更新 + 服务端持久化）
```

- LLM **不直接输出具体起止时间**，只输出任务（时长、频次、偏好、优先级）与约束；时间由引擎计算。
- AI 编辑同理：LLM 输出 Patch 操作（语义级，如 `move_block`、`add_task`、`set_constraint`），引擎执行并重新求解受影响范围。
- 所有 LLM 结构化产物必须通过 JSON Schema 校验 + 业务校验（时长>0、窗口合法等），校验失败自动要求模型重试（上限 2 次），仍失败则向用户呈现可读错误并保留对话上下文。

### F2 约束模型与排程引擎（P0）

**约束类型（v1 固定集合，Schema 见附录 A）：**

| 类型 | 语义 | 示例 |
| --- | --- | --- |
| `busy_window` | 固定忙碌窗口，不可占用 | 周三 18:00–22:00 兼职 |
| `active_window` | 每日可安排时段 | 每天 07:00–23:00 |
| `daily_cap` | 某分类每日时长上限 | 学习 ≤ 6h/天 |
| `mutex` | 两个主体（分类或任务）不得同日相邻/同日出现；默认软、可切硬 | 数学与英语不连续安排（task 级） |
| `preferred_period` | 任务偏好时段（软约束） | 背单词放早晨 |
| `buffer` | 任务间最小间隔 | 两块之间 ≥ 15min |
| `fixed_block` | 用户钉死的时间块，引擎不得移动 | 周六 14:00 模考 |
| `deadline` | 目标截止日，用于倒排与冲刺节奏 | 12 月 20 日考试 |

**任务定义字段**：标题、分类、单次时长、频次（每周 N 次 / 每天 / 一次性）、优先级（高/中/低）、弹性（固定/可移/可拆分）、偏好时段。

**引擎规则（确定性、可单测）：**

| 编号 | 规则 |
| --- | --- |
| F2.1 | 硬约束（busy/active/daily_cap/fixed/mutex-hard）永不违反；软约束（preferred/mutex-soft）尽量满足，违反时在方案中标注"妥协项" |
| F2.2 | 落位顺序：fixed_block → 高优先级且窗口受限任务 → 其余按优先级+偏好贪心放置，同分按稳定序 |
| F2.3 | 支持跨天分配与"可拆分"任务的切块（单块 ≥ 25min） |
| F2.4 | 无解时输出**冲突报告**：哪条约束/哪个任务放不下、原因、建议（放宽哪条、缩短多少），绝不静默丢任务 |
| F2.5 | 重排最小化：局部编辑只重排受影响任务块，`fixed_block` 与用户手动钉住的块不动 |
| F2.6 | 引擎为 shared 纯函数模块（前后端同源双端运行），输入输出均为 JSON，附单元测试（≥ 12 个用例覆盖各约束类型与无解分支）；服务端提交时重算为权威 |
| F2.7 | 时区：默认取浏览器时区并允许修改；所有存储为 UTC + 计划时区字段 |

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F7.1 | 免登录：首次访问由平台签发匿名访客身份，Function 端 `requireUser(ctx)` 验证；前端不实现任何账号 UI | P0 |
| F7.2 | 数据归属：计划、对话、约束、模板、点赞均绑定访客 ID，服务端强制归属校验，跨访客读写一律 403 | P0 |
| F7.3 | 恢复码：设置抽屉可生成一次性恢复码（展示一次，服务端存哈希）；新设备输入恢复码后认领原访客数据（合并策略：恢复码优先，当前设备数据提示导出后覆盖） | P1 |
| F7.4 | 本地缓存：日历视图偏好、草稿输入存 localStorage；**业务数据以服务端为准**，本地仅做乐观缓存 | P0 |
| F7.5 | 隐私声明页脚：说明匿名收集范围（计划内容、对话内容）、不收集邮箱/手机号，提供"删除我的全部数据"入口（二次确认，服务端级联删除） | P0 |
| F7.6 | 数据保留：访客 180 天无访问，其私有计划与对话自动清理（模板保留，作者显示"已注销访客"） | P2 |

### F8 引导与状态体验（P0）

| 编号 | 需求 |
| --- | --- |
| F8.1 | 首次进入：3 步轻量引导（可跳过）指向对话输入框、日历、社区入口；不遮挡核心操作 |
| F8.2 | 全链路状态：AI 初始化中 / 生成中（流式光标+骨架日历）/ 等待确认 / 完成 / 失败（可读原因+重试按钮）/ 中断 |

| F8.5 | 所有 AI 输出文本经转义/净化 Markdown 渲染，防 XSS；不渲染原始 HTML |

## 7. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 首屏 LCP < 2.5s（公开 URL 实测）；日历 100 块拖拽 ≥ 50fps；SSE 首 token < 3s（P95，上游正常时）；排程引擎单次求解 < 200ms（7 天 × 50 任务） |

| 可访问性 | 键盘可达全部核心操作（对话、确认卡、日历块选择与移动提供键盘替代：选中块后方向键移动）；对比度 ≥ 4.5:1；分类色盲双编码 |
| 兼容 | Chrome / Edge / Safari 最近两个大版本；移动端 375px 起可用 |
| 可观测 | Function 关键边界记录安全诊断 ID（不含凭据/原文），错误翻译为用户可读文案 |
| 视觉 | 独立设计系统（后续 UI 规范定义）：以"时间/秩序/生长"为意象的主色族 + 语义色；日历为视觉主角；动效服务于状态反馈（落位、冲突、diff），克制不炫技 |

## 8. 技术架构约束（供技术方案文档展开）

```
浏览器（React SPA，静态构建产物）
  │  同源 fetch / SSE
  ▼
Qoder Sites `app` Edge Function（Deno）
  ├── 身份：requireUser(ctx) 匿名访客验证
  ├── 路由：/api/chat（SSE）、/api/plans、/api/blocks、/api/constraints、
  │         /api/patches、/api/templates、/api/recovery、/api/export
  ├── 排程引擎：shared 纯函数（服务端权威重算；前端同源即时预览，共享校验 Schema）
  ├── QCA 客户端：平台 Managed 客户端 + sse 助手，apiOrigin 取自 get_context
  └── 持久化：Function 后端数据库（应用自建会话映射/历史/游标/配额表）
  ▼
Qoder Cloud Agents（Managed SSE，/api/v1/cloud/*）
```

**数据实体草案（详细 Schema 在数据模型文档定稿）：**

- `plans`：id、owner_visitor_id、title、horizon_start/end、timezone、status、source_template_id、时间戳
- `blocks`：id、plan_id、title、category、start/end（UTC）、priority、flexibility、pinned、notes、recurrence_ref
- `task_defs`：id、plan_id、title、category、duration_min、frequency、priority、splittable、preferred_period（排程输入，与落位后的 blocks 区分）
- `constraints`：id、plan_id、type、payload(JSON)、source(user/ai)、enabled
- `conversations`：id、owner_visitor_id、plan_id、qca_session_id、status、last_cursor
- `messages`：id、conversation_id、role、content、created_at
- `dispatch_intents`：幂等派发记录（request_id 唯一、状态 pending/done/failed，用于对账）
- `templates`：id、author_visitor_id、title、description、tags、snapshot(JSON 脱敏结构)、status、use_count、like_count、时间戳
- `template_likes` / `template_uses`：幂等计数明细
- `recovery_codes`：visitor_id、code_hash、used_at
- `quotas`：visitor_id、date、chat_turns、publishes

**关键服务端契约：**

1. 会话初始化懒加载：仅在授权的"开始/发送" POST 后创建 QCA 资源；页面加载与重连只复用既有绑定。
2. 消息发送携带稳定 request_id；202 表示受理；SSE 投影允许的消息/状态事件，持久化历史与游标后关闭上游流。
3. LLM 结构化产物（约束提取 / Patch）以专用消息类型返回，服务端 Schema 校验后才进入引擎。
4. 模板套用 = 复制 snapshot → 新计划 task_defs/constraints → 走正常采集+排程，不复制 blocks 绝对时间。

## 11. 风险与开放问题

| # | 风险/问题 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | QCA 联网检索工具可用性未确认 | F1.5 | M2 前用 get_context + 实际会话验证；不可用则降级为模型知识并在 UI 明示，不阻塞 P0 |
| R2 | 匿名身份跨设备能力有限 | 数据找回 | 恢复码（F7.3）+ JSON 导出兜底；隐私页明示"清数据前请导出" |
| R3 | LLM 结构化输出不稳定 | 排程失败率 | Schema 校验 + 2 次自动重试 + 可读失败兜底；约束类型集合收敛为 8 种降低复杂度 |
| R4 | 排程无解场景体验 | 用户挫败 | 冲突报告 + 一键"放宽建议"（生成约束修改 Patch 走确认） |
| R5 | 公开站点滥用（刷对话/刷模板） | 配额成本 | 服务端限流 + 每日配额 + 发布审核；异常访客可封禁（P2 管理端） |
| R6 | 模板内容提示注入 | AI 被劫持 | 模板数据入提示词时隔离标记 + 输出仅限 Schema 化 Patch，引擎兜底校验 |
| R7 | 大赛工期 | 范围蔓延 | 严格按 P0→P1 顺序；P2 一律不进提交版本 |

**待评审决策点（v0.2 已关闭 1、2；3–5 仍开放）：**

1. ✅ 已拍板：MVP 时间范围 7/14 天，30 天移出 MVP。
2. ✅ 已拍板：mutex 默认软（同日不相邻）、确认卡可切硬；主体支持分类或任务 key（`subjects.kind`）。
3. 社区是否允许游客（未生成过计划者）点赞？建议允许（降低互动门槛），发布必须实名计划来源。
4. 恢复码认领的合并策略是否采用"覆盖当前设备"？建议覆盖前强制提示导出。
5. 视觉方向与品牌色：待 UI/UX 规范文档定稿（候选意象：晨光时间轴 / 生长年轮）。

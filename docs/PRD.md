## 0. 一页概要

### 0.1 产品定位

**让用户从“我想做一件事”，走到“我知道怎么做、何时做，并且能持续推进”。**

用户以简短的自然语言对话描述目标；Agent 动态澄清必要条件，必要时查找和核对信息，生成**有来源、有约束、可修改**的行动计划；用户审批后，系统将任务排入 App 内置日历、设置提醒、记录执行反馈并在条件变化时提出局部调整。用户的规划**方法/路径**可保存为私人模板；未来符合执行记录要求并通过隐私与质量审核后，才允许发布可供他人应用的模板。

核心闭环：`目标内聊天 → Agent按需澄清/研究 → 方案草稿（含拟安排） → 一次确认并自动入历 → 提醒/执行 → 反馈 → 对话修改与差异批准`。

**2026-10-11 用户明确确认的交互**：规划主流程仅聊天与最终方案草稿。条件由Agent提问、harness从用户回答受控提取并保存，Slot是内部数据，不要求用户填表或逐项确认字段。研究/搜索/证据选择/生成由后台编排，必要补问和失败在聊天说明。用户确认包含拟安排的方案后，确定性业务服务自动排入内置日历；不另设正常路径的第二次排程审批。实现改造及批准边界见[对话主流程](CHAT_FIRST_FLOW.md)，现有表单为过渡测试能力，尚未完成此体验。

### 0.2 已确定的产品决策

- **通用目标产品**：支持学习、健身、护肤及其他生活目标；不是护肤/健身垂类应用。
- **iOS-first**：首个正式客户端为 iPhone App；目标、聊天、计划、内置日历与提醒是主要页面。
- **隐私优先**：不持续读取屏幕、位置、邮件、通讯录或全量日历；按当前目标采集最少必要信息。
- **以 Goal 而非 Chat 为中心**：会话用于澄清/修改；真正持久化的是目标、约束、计划版本和任务。
- **计划可验证和可追溯**：Agent 负责语义理解和建议，业务规则负责校验排程；高影响改动经过用户确认。
- **21 天不是养成保证**：适用于持续性目标的**默认启动观察期**（可改），不适用于所有目标；不能宣称 21 天即可形成习惯。
- **模板是路径，不是私人计划副本**：复用条件化提问、研究策略、任务结构，不复制原作者个人数据。
- **个人开发者可维护**：优先完整闭环，不追求一开始做社交网络、云电脑、全自动外部操作。

### 0.3 版本承诺

| 阶段 | 核心目的 | 必须交付 | 不包括 |
| --- | --- | --- | --- |

## 1. 问题与机会

### 1.1 用户待解决问题

1. 有想法但缺少领域知识，不知道如何问、如何选、第一步做什么。
2. 通用聊天 AI 给出文本方案后，用户仍要手动拆任务、规划时间、创建提醒。
3. 现实条件会变化：时间、预算、能力、资源改变时，静态计划很快失效。
4. 他人的“现成计划”可能不适用于自己；分享者也缺少将经验抽象成**可迁移方法**的工具。
5. 打卡数不等于目标达成；用户缺少解释性反馈和版本记录。

### 1.2 目标用户

| 用户画像 | 情境 | 价值 |
| --- | --- | --- |
| 陌生领域初学者（核心） | 想增肌/护肤/学习，但不懂方法 | 少查无效信息、明确行动起点 |
| 有计划却难推进的用户（核心） | 想把任务融入真实生活 | 一次确认后进入日历和提醒 |
| 日程经常变化的用户 | 临时加班、课程更换 | 快速提出重新安排的可选方案 |
| 模板贡献者（V0.3） | 走过完整计划，愿意分享经验 | 将方法脱敏发布供他人复用 |

**待验证假设**：早期用户愿意花约 3–8 分钟完成首次目标澄清；这不是已验证的体验指标。

### 1.3 差异化假设（非已验证竞争优势）

- 相对通用聊天助手：结果不是一次性的文字，而是**可执行且可维护的结构化计划**。
- 相对智能日历：价值起点在日历**之前**——领域研究、必要信息澄清和方案选择。
- 相对固定内容模板：复用的是条件化决策路径，实例化时动态补问、重新核查过期资料。
- 相对全面上下文型私人助理：围绕**当前目标**收集有限信息，不把广泛采集用户生活数据作为前提。

### 1.4 明确不做

- 不持续监视用户设备；不自动读取所有 App、邮件、照片和生活数据。
- 不自动购买、支付、代发消息或替用户修改外部日历。
- 不代替医疗/营养/药学诊断与处方；不保证特定身体效果。
- 不提供“21 天养成习惯”保证；不使用惩罚性连续打卡规则。
- 不把未经审核的用户模板作为事实或专业证据；不发布原始聊天/健康参数。

## 2. 产品原则与安全分级

1. **少问但问对**：根据已知 Slot、风险和信息收益选择问题；必要安全信息缺失必须停止高风险方案定稿。
2. **分离事实/假设/建议**：研究信息要有来源、核验时间及适用范围；不确定时明确表示。
3. **每一步可修正**：用户可修改条件、拒绝单条建议、暂停或删除目标；修改尽量局部化。
4. **确认先于生效**：生成计划≠写入日历；排程预览、影响说明和确认不可省略。
5. **最小权限**：通知单独授权；系统日历可选且不是 MVP 必需功能。
6. **人类最终决策**：AI 不默默决定开销、药物、健康风险或已确认的外部承诺。

**目标风险路由建议**：

| 级别 | 示例 | 处理 |
| --- | --- | --- |
| L0 普通 | 读书、练习、整理、日常习惯 | 可生成并安排，仍需用户确认 |
| L1 有一般专业性 | 常规健身、基础护肤、非医疗营养信息 | 展示依据、不确定性及适用条件；必要时谨慎提示 |
| L2 高影响/高度个性化健康 | 已知伤病训练、药物与饮食相互作用、症状判断 | 额外安全澄清、限制自动建议；需要专业人员判断时转介 |
| L3 不支持自动规划 | 处方调整、危险行为、紧急医学处理等 | 不自动执行/安排高风险行动；给出恰当安全指引 |

类别不是静态的：同一个“健身”目标可因用户条件从 L1 转成 L2。不得通过社区模板降低安全级别。

## 4. 核心用户旅程

### UJ-01：从模糊目标开始（健身示例）

1. 用户输入“我想开始健身，想增肌，但不知道怎么练、怎么吃”。创建 `Goal(draft)`。
2. Agent 推断必要信息：目标与范围、经验、训练环境、时间窗口、预算、必要安全限制；能复用当前 Goal 内已确认信息。
3. 提问优先补齐**阻止执行的缺失信息**；可选信息允许“暂不确定”；允许随时补充新条件。
4. 必要的歧义通过聊天澄清；后台开展子问题研究：训练方法、饮食基础、是否真的需要补剂、价格与适用条件。
5. 生成 `PlanDraft`，标注依据、前置条件、风险、任务时长/频率及粗略投入；采购建议不等于自动购买。
6. 用户通过聊天提出修改或替代方案；后台保留原稿与不可变变更，不要求逐项填写数字表单。
7. 排程服务根据**App内固定事件及聊天获取的具体可用时间/时区**检查候选安排，合并展示在最终方案草稿；缺项或冲突回聊天补问，尚不写入日历。
8. 用户一次确认方案及拟安排后，业务服务复查版本/冲突并原子生成 `PlanVersion(active)`、`ScheduledOccurrence`；自动入历，客户端按最终日程同步本地提醒。
9. 用户通过任务详情或提醒反馈“完成/部分完成/跳过/延期”；状态与目标进度可查看。
10. 用户说“周一晚上以后没有空”→ 系统生成 `PlanRevision` 的差异预览、重新校验候选时段，审批后生效，并同步提醒。

### UJ-02：初期学习计划（无购物）

用户输入“六周后要参加考试”→ 澄清考试与水平、可投入时段 → 查证学习资源 → 分阶段计划 → 考前模拟与复习安排 → 日历 → 根据练习反馈调整。**证明通用内核不是围绕购物设计的。**

### UJ-03：21 天观察期（V0.2）

为持续型目标默认提供“21 天启动计划”选项；用户可改为 7/14/自定义。第 7、14、21 天可产生复盘提醒；观察期结束后允许继续、调整或暂停。单次旅行/紧急截止目标按真实期限，不强制 21 天。

### UJ-04：模板路径复用（V0.2 私人；V0.3 公开）

创作者完成某 Goal → 提取 Slot schema、分支规则、研究策略、任务骨架 → 手动检查脱敏内容 → 保存私人模板；公开资格另行验证。新用户应用时填写必要条件，Agent 动态补问并查证新资料，生成独立计划，不直接复制创作者的身体数据、日历事件或执行记录。

## 5. P0 详细功能需求与验收标准

### FR-01 账号、目标生命周期

**需求**：登录/会话、创建并恢复 Goal 草稿；目标状态 `draft → clarifying → researching → review → active ↔ paused → completed / archived`；允许删除。

**验收**：
- 关闭 App 后重新打开可恢复 Goal、已确认 Slot 与研究任务状态。
- 重复点击创建/确认操作不产生重复目标或重复日程（幂等）。
- 目标删除时先提示影响，关联私人计划与提醒按删除策略清理；个人数据可导出/删除。
- 用户不会读到其他用户的私有 Goal；服务端鉴权覆盖每条相关 API。

### FR-02 动态澄清

**需求**：Slot是内部结构，不在普通主流程显示表单；Agent询问并由harness记录用户明确回答，歧义通过聊天补问。每个 Goal 的 Slot 有 `key/value/required/source/confirmed/sensitive/updated_at`；Agent 在**已知信息、信息增益、风险**基础上选择下一个问题；支持按钮选项、自由输入、未知/跳过。

**验收**：
- 不无故重复问已确认字段；矛盾输入要求澄清并显示采用的最终值。
- 首轮可采用建议性的 3–6 轮软预算，无法满足安全条件则延长，而非跳过。
- 关键必填项缺失时不得最终入历，允许生成标注假设的初稿。
- 用户新信息触发相关 Slot 更新并标记受影响的研究和任务，而非必然重做全部。

### FR-03 研究、来源与风险控制

**需求**：拆解研究问题；按需要调用搜索与可信网页读取工具；保存 `Evidence` 的 URL、访问时间、证据类型、具体支撑的 claim 及适用限制。

**2026-10-11 用户确认的方案方法**：组合使用目标倒推、约束规划、按需检索、生成后校验/修订与执行反馈。先明确达成标准和必要条件，再拆阶段、任务及依赖；只有需要外部事实/时效性资料或已知依据不足时检索，不强制每个目标联网搜索。检索供应商通过可替换接口接入，DeepSeek继续负责澄清与分析，harness控制流程/权限/预算/恢复；供应商选型与费用对比见[搜索实现策略](SEARCH_STRATEGY.md)，推荐不等于已接入或实测胜出。

正式流程为：聊天采集条件 → 后台判断知识缺口/按需研究 → 生成PlanDraft → 校验并修订/确定性拟排程 → 草稿内一次确认 → 自动入历 → 执行反馈与对话局部重规划。手动来源页作为补充/测试入口，Agent组织查询是后续主研究流程；当前来源重读任务不等于已经实现自动搜索。

**验收**：
- 计划中涉及明确外部事实/商品价格/专业效果的关键主张可找到引用或标明未核实。
- 不将商品成分列表直接推断成准确浓度，不把“网上有人这样做”作为专业论据。
- 搜索失败、访问被拒、来源冲突均告知用户；绝不谎称已经核验。
- 网页和模板内容一律视为不可信数据，不能触发未授权工具调用。
- 健康、药物及补剂请求执行第 2 节风险分级；不提供个体化处方决策。

### FR-04 结构化计划

**需求**：输出目标摘要、重要假设、阶段、任务、时长、频率、时间窗口、资源、依赖、成本/风险/依据；计划可按任务编辑。

由验收结果倒推任务，并按用户已确认时间、预算、水平、资源及限制裁剪。有合理取舍时可给出最多两种候选草稿（例如较少投入/较多投入），解释差异和适用条件，不宣称存在无需验证的唯一最佳方案。生成与审阅可由同一Provider分步骤完成；模型自检不代替引用核对、领域安全或确定性排程。执行反馈用于调整未来任务，不覆盖既有执行历史；尚未确认的假设必须显式标出，不能自行补成用户事实。

**验收**：
- 每条 Task 有稳定 ID、预计时长、任务类型与依赖；明确 `mandatory/optional`。
- 采购/准备/报名等前置事项可被标记为 blocked，不能直接视作已完成。
- 展示大致所需预算、每周时间与尚未确认的条件。
- 用户可拒绝某条建议并局部重生成，不必丢掉已接受任务。

### FR-05 App 内日历与排程

**需求**：App 内日历是唯一首版排程事实源；固定事件可在日历自行维护，可用时间主要通过Agent聊天获取。柔性任务由排程引擎计算候选，合并在最终方案草稿；用户一次批准该方案及安排后自动入历。首版**不需要**读取 Apple Calendar。

**验收**：
- 任务默认不可与另一占用型任务重叠；安全的并行关系需要显式条件，不基于“吃饭和吃药能同时做”等泛化推断。
- 固定事件未经授权不被移动；柔性任务遵守硬约束（时间窗、先后依赖、最小间隔、前置条件）。
- 无法排程时返回明确原因和可操作备选项；不要凭空创建不存在的空闲时段。
- 正确处理时区、跨午夜、夏令时变化与周期性 occurrence。
- 新计划拟安排在最终草稿内预览并一次确认；修改生效日程展示差异再批准。确认时若版本/日历变化则拒绝并重新审阅，不静默改变已批准安排。

### FR-06 iOS 通知与任务反馈

**需求**：`expo-notifications` 负责本地提醒、权限请求和通知响应；按任务时间更新本地提醒；支持提醒提前量、静默时段（产品策略）以及关闭通知。

**验收**：
- 用户允许通知后，已有未来 occurrence 可以预先在设备调度本地提醒；系统权限拒绝时 App 仍能使用日历。
- 改期后在客户端取消旧提醒并重新调度；重复同步不创建多个同一提醒。
- 用户反馈 `completed / partial / skipped / postponed / unknown`；“已安排/已展示通知”不视作完成。
- App 离线仍可读取已缓存的基本任务，客户端可暂存反馈并在联网后幂等同步（如离线支持未实现，MVP 初期要明确展示需要联网）。
- iOS 专注模式、系统权限、关机和系统调度可能影响提醒；不承诺精确必达。

### FR-07 自然语言修改与计划版本

**需求**：识别“我周一不能练了”“预算只有 100 元”等变化，生成**待批准**的 PlanRevision 和 ScheduleProposal；比较增删改移，明确理由及额外成本/风险。

**验收**：
- 在用户确认前当前生效版本及日历不受修改；乐观锁拦截陈旧确认。
- 版本生效时数据库中的计划版本、日程实例以事务保证一致；通知属于后续设备同步过程，不宣称跨设备事务原子性。
- 仅修改相关项，不无故移动无关任务；无法安排时可维持原计划并解释原因。
- 用户可查历史版本，回退也必须重新校验当前时段。

### FR-08 设置、隐私与可访问性

**需求**：调整通知、查看/纠正当前目标 Slot、暂停任务、导出/删除个人数据；基本无障碍/大字体支持。

**验收**：
- 默认不读取系统日历与其他 App 数据；上传模板默认关闭（P2）。
- 敏感目标名称可以选择通知隐藏预览；日志不得记完整私人聊天和敏感 Slot。
- 删除账号与删除单个 Goal 有明确流程和错误反馈；用户撤销授权后停止新增通知。

## 6. P1 / P2 需求

### FR-09 21 天 Kickstart（V0.2）

- 对**持续性**目标建议默认 21 天，可改 7/14/21/自定义；短期/一次性目标按实际周期，不强制启动计划。
- 独立显示 `elapsed_days`（经过天数）、`feedback_days`（用户有记录的日数）、`scheduled_count`、`completed_count` 和 `outcome_notes`（实际变化描述）。
- 第 7/14/21 天提供可跳过的阶段复盘，允许暂停与修改；逾期/跳过不惩罚性清零。
- “完成 21 天”仅指观察期满足定义，不等于习惯形成或效果已经证明。

### FR-10 私人模板路径（V0.2）

- 由计划与修订历史抽取 `InputSchema`、`ConditionalQuestions`、`ResearchPolicy`、`TaskBlueprint`、`SafetyRules`；用户逐项检查再存储。
- 原作者私人数据值不进入可复用模板；模板应用者填写自己的必需字段，Agent 可额外补问。
- 模板变更不自动改变由旧版模板生成的已有计划；保留 `origin_template_version_id`。

### FR-11 公共模板分享与发现（V0.3）

- 延续用户设想：**持续型模板须创作者先经历至少 21 个自然日的执行观察，方可申请公开**。具体额外反馈门槛待真实用户验证；建议初期试验“至少 14 个不同自然日有明确状态反馈”，**该数字不是最终规则**。
- 创作者申请时进行自动化 PII 脱敏预检查 + 人工审核（或早期管理员审核）；创作者须预览公开内容、确认发布。
- 模板标签使用“创作者有执行记录 / 已通过内容检查”，不能说“科学认证有效”。
- 搜索、筛选、举报、撤回、修改发布新版本；社区展示需符合 App Store UGC 管理要求。
- 不适合 21 天观察的一次性目标可保存私人模板，其公开资格另行设计，不强行套用。

### FR-12 多目标协调与系统日历（V0.4+）

- 多 Goal 共同使用同一个 App 内日历，冲突可发现；复杂的跨目标优先级自动权衡后置。
- 未来可选择性读写 Apple Calendar；仅写入不等于允许读取冲突，必须单独申请相应权限。
- 后期远程推送用于跨设备/服务器触发场景，不能替代 P0 的本地提醒。

## 7. 排程和并行规则

**核心概念**：
- **Hard Constraint**：时间不可重叠、截止时间、依赖、可用时间范围、资源互斥、安全禁忌等；不可违反。
- **Soft Constraint**：偏好傍晚、尽量保留习惯、减少日程改动、均匀分布等；可优化。
- **Task**：可重复的动作定义；**Occurrence**：某天某时的一次执行；**CalendarEvent**：固定占用。

| 冲突类型 | 示例 | 处理 |
| --- | --- | --- |
| 时间 | 晚间训练与会议重叠 | 换候选时间、不能强排 |
| 资源 | 两项任务都需独占双手或场地 | 默认不并行，显式白名单后才可兼容 |
| 先后依赖 | 还未买到必要材料就安排使用 | blocked / 等待前置 |
| 最小间隔 | 需要恢复或相互间隔的任务 | 根据可靠规则验证、必要时征询用户 |
| 风险/条件 | 某药是否可随餐不明确 | 不推断可同时进行，转为核实/专业咨询 |
| 改期 | 任务延迟影响后续任务 | 展示被波及的 occurrence 与通知更新 |

首版采用**确定性贪心/约束规则**排程即可（窗口离散化 + 约束过滤 + 候选评分），不必一开始做 CP-SAT 优化；若基本用例失败率高再迭代。用户手动选择始终高于算法偏好。

## 8. 通知与反馈业务规则

- 提醒默认建议：每项任务“提前一次 + 到点一次”**可配置**，避免催促疲劳；开启前获得 iOS 通知授权。
- App 内未来 occurrence 是事实源；设备通知只是衍生提醒。不依赖手机退到后台后继续运行 JS 定时器。
- 使用滑动时间窗口安排将来的设备本地通知，避免一次性为无限重复任务全部创建；窗口长度作为技术参数验证。
- 计划更改后写入 `notification_sync_required`，App 在接收更新或重新打开时完成取消/重建和状态上报。若 App 没有运行且服务端计划已经变更，旧本地通知可能仍存在；应通过“客户端确认后提交”以及日后的远程推送/同步策略缩小不一致窗口。
- 后台通知交互响应需兼容用户点开 App 后补写反馈；通知被展示 ≠ 用户确认完成。
- 用户关掉通知后仍能从 App 查看待办。敏感任务名支持隐私预览。

**反馈状态**：`unknown` / `completed` / `partial` / `skipped` / `postponed`；每个操作要有幂等 ID、可编辑/撤销策略，重复提交不能重复算进度。

## 9. 模板：复用的对象与生命周期

### 9.1 模板必须携带

`GoalCategory`、`Applicability`、`RequiredInputs`、`ConditionalQuestions`、`ResearchStrategy`、`TaskBlueprint`、`SafetyAndReviewRules`、`SchemaVersion`、`Provenance`（数据来源/创建者执行观察记录）、`PublicationStatus`。

**模板明确不携带**：创作者具体健康数据、原始聊天、私有日历、通知设备 Token、付款凭证以及独立计划中的敏感字段值。

### 9.2 私人/公开生命周期

`private_draft → private_ready → eligible_for_submission → pending_review → published → withdrawn/rejected`。

- `eligible_for_submission` 是可申请，并非平台认可有效；不把 21 天经过当作结果证明。
- 发布后模板版本不可静默修改；改动生成新版本，已有用户的 Plan 不自动迁移。
- 应用模板等同于“执行新的澄清→研究→计划→审批”，不等同于一键复制日程。
- 对错误建议/侵权/泄露隐私提供撤回、举报和管理员审计。

## 11. 数据/安全/合规

- **权限最小化**：App 内日历不要求系统日历权限；通知授权在首次真正安排提醒前询问。
- **健康领域**：身体参数、药物/病史属于潜在敏感信息；按目的最小化收集、单独说明，不默认公开或用于模板聚合；高风险请求升级处理。
- **研究透明**：显示来源链接、检索日期、不确定项。外部信息和社区模板均是不可信输入，不可提升到系统指令。
- **服务器端密钥**：LLM Key、搜索 API Key、数据库服务密钥不出现在 iOS App 中。
- **隐私可控**：用户可编辑 Slot、关闭通知、撤销授权、导出/删除计划及账户；公共模板独立申请发布。
- **账号删除**：按 App Store 和数据处理政策提供 App 内删除入口与后台清理方案；采用 Apple 账号登录时遵守相应规范。
- **UGC 审核**：V0.3 上线前完成举报、屏蔽/下架、内容过滤、联系渠道及发布审核机制。
- **供应商透明**：上线前披露模型、搜索及存储服务中数据处理与保存情况，依据目标市场开展必要的法律/隐私审查。

## 12. 关键指标与用户研究

**北极星（候选）**：`Weekly Progressed Goals`：最近 7 天存在至少一次用户确认的真实执行反馈、且仍在推进的目标数。只是行为参与度代理指标，**不等于目标效果**。

| 阶段 | 观察指标 | 备注 |
| --- | --- | --- |
| 目标创建 | 创建完成率、退出原因 | 不应强迫填写不必要的个人信息 |
| 澄清 | 回合数、重复问题率、缺字段率 | 优先质量，非一味缩短提问 |
| 研究 | 来源可核查率、搜索失败率、单次成本 | 统计前先明确定义口径 |
| 计划 | 草稿接受率、修改率、接受原因 | 看用户是否相信并理解 |
| 排程 | 入历率、硬约束拦截数、无法排程原因 | 确认前不得改日历 |
| 执行 | D7 有效反馈率、完成/跳过/未知 | 不把“已提醒”算“完成” |
| 变更 | 局部重规划成功率、回滚率 | 看计划是否真的可维护 |
| 模板（后期） | 复用后成功入历率、适配失败率、投诉率 | 不把下载量等同于质量 |

**首次验证场景**：学习备考、健身入门（含补剂研究但不强推购买）、基础护肤。建议找 10–20 位不同习惯的早期试用者进行探索性研究（非统计意义的效果结论），观察是否愿意实际将计划入历并执行。

## 13. 非功能要求与成本边界

| 维度 | 需求与验证 |
| --- | --- |
| 可靠性 | 幂等 API；持久化研究任务；重试不重复插入日程；版本确认使用乐观锁 |
| 易恢复性 | App 重启、网络失败、后台研究服务重启后状态可恢复 |
| 可解释性 | 研究结论有出处、变更有 diff、冲突有原因码 |
| 数据安全 | 服务端鉴权、分层授权、对象授权/数据库最小权限、传输加密、密钥托管 |
| 可观测性 | 记录匿名化运行状态、Token/工具用量、错误种类，不记录敏感聊天正文 |
| 性能 | 非 AI 页面优先流畅；Agent 阶段性进度可见，不编造固定秒级完成保证 |
| 可用性 | iPhone 常见屏幕尺寸适配、Dynamic Type/VoiceOver 基本可达性、网络不可用提示 |
| 成本 | 单次 AgentRun 的模型 Token/工具调用/搜索次数有预算上限与超额处理 |

**首版不人为写入未验证的 99.9% 可用率、固定研究完成时长、留存提升数值**；基于真机和部署环境测试后再制定 SLO。

| AC-10 | 健康风险信号 | 阻止高风险自动执行，提供合适安全说明 |
| AC-11 | 重复提交执行反馈 | 一条 occurrence 的同一请求仅计算一次 |
| AC-12 | 两端几乎同时确认不同版本 | 版本冲突可解释，不能静默覆盖 |
| AC-13（V0.2） | 两人复用同一私人模板 | 动态问题及产出不同，不复制原作者私人字段 |
| AC-14（V0.3） | 21 天未满即申请公开 | 不允许提交；满足资格后仍需脱敏及审核 |

## 16. 重要未决问题（下一轮讨论）

1. **首发地区与语言**：仅中文 / 多语言；不同地区健康内容与隐私法规可能不同。
2. **认证体验**：MVP 使用邮件验证码/魔法链接还是 Apple 登录？要考虑真实用户转化与苹果审核规则。
3. **成本与商业模型**：免费目标数、每月研究次数、深度搜索是否计费；**目前没有定价决策**。
4. **研究可靠性**：哪些领域/来源必须加强校验，商品对比信息保存多久视为过期？
5. **通知策略**：最小提前量、静默时间、自定义规则；真实 iPhone 上的行为需测量。
6. **模板上传门槛**：≥21 天加反馈覆盖率的建议门槛是否合理，有无刷记录风险？
7. **执行效果评估**：如何区分完成计划和真正取得成效？
8. **范围裁剪**：若 MVP 超出个人开发能力，优先降低研究领域复杂度，而不是省略审批/权限/安全校验。
9. **合规/用户年龄**：是否面向未成年人，是否允许高风险健康模板公开？默认不主动覆盖高风险领域。
10. **外部日历**：V0.4 是否真的需要读 Apple Calendar，还是聊天获取可用时间已经足够？

## 17. 资料与术语

- **Goal**：总体目标；**GoalSlot**：某目标所需的具体用户条件。
- **PlanVersion**：一版结构化可执行方案；**ScheduleProposal**：尚未确认的时间安排建议。
- **Task**：任务定义；**Occurrence**：某一次实际排入的执行实例。
- **PlanRevision**：修改差异；**Template Path**：条件化的规划流程，不是固定日历副本。
- **Kickstart**：可调长度的执行启动观察期，21 天是默认建议而非效果承诺。
- **Hard / Soft Constraint**：必须遵守的限制 / 尽可能满足的偏好。

## 2026-10-11 澄清停止与最低信息要求

用户明确要求至少询问三个最重要的信息点：期望成果、可投入时间、当前基础/资源与关键限制。同一字段重复追问不算多个信息；允许未知，不强迫提供确定答案。三个不同信息点至少各问一次后可「停止提问，先出草稿」，随后基于已有信息生成带待核对假设的草稿，不继续强制问答。未知或委托不当作空闲时间；安全与排程关键缺项仍阻止最终批准入历。当前停止已接持久自动研究与草稿生成首批链路，只有真实成功才展示草稿；失败/未知不重复调用或显示假成功。完整领域校验、自然语言改稿与批准入历仍待实现。

### 2026-10-13 用户流程修正：先给方案与建议日程

用户明确要求不再先追问具体可用时段：Agent顺着已有对话直接制订方案并附候选时间，用户再追加无空时段/偏好进行局部调整。未知时间用明确披露的默认时区与时段假设，不冒充用户事实或已核实空闲；已记录固定占用仍确定性避让。安全关键条件及最终具体方案批准保留，确认前不写生效任务日历。这取代“没有可用窗必须先问”的常规门槛，不改变三Tab、品牌、版本/历史和模型不能直接写核心表的规则。实现边界及验收见[TODO](TODO.md)。

### Guidy！卡片式入口与日历结果（2026-10-13 用户明确指定）
